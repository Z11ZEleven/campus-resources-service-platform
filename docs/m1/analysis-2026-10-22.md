# M1 現況與 PLAN_M1 全盤分析

日期：2026-10-22。分析基線：`feat/m1-t01-t05-foundation`，HEAD `f7f8dc5bf63bea12d5e6213e90400bcd2731539d`。

本報告以 [PLAN_M1.md](../PLAN_M1.md) 為主線，核對現有程式、遷移、測試、需求及課程任務書。僅新增本份 M1 分析，不修改 M1 業務程式、公共層、M2、M3 或原 PLAN；以下建議不是團隊決議，也不是後續功能的實作授權或人工驗收。

## 1. 整體判斷

**PLAN 的主體架構可以繼續使用，但應先校準成「以現有工程增量開發」的執行基線。** 目前完成的是 T01–T05 的工程基礎，學生尚不能透過 M1 完成搜尋、預約、取消、簽到與歷史復用的業務閉環。

值得保留的方向：

- M1 與 D 資源使用同一資料庫交易；預約和來源占用一起成功或回滾。
- 房間鎖統一裁決，使用半開區間，提交時重檢真實來源。
- 每種限制保留來源，釋放只處理指定來源；投影不是預約成功依據。
- 提醒觸發、違約、簽到與預約狀態由 M1 決定，D 提供統一身分、投遞及審計。
- 真實 MySQL、故障恢復、跨模組網路與破壞性驗證列入驗收。

執行前最需要處理的是：文件契約不一致、時間與教室分類規則未收斂、公共持久化任務尚不存在，以及目前資源入口與新 M1 最小權限之間的差異。不能用「5/17 任務完成」推算業務完成度或剩餘工期；後續狀態機、可靠任務與整合工作量明顯較大。

## 4. PLAN 應優先校準的問題

優先級是後續建議：P0 為進入相關業務前必須明確，P1 為對應功能交付前必須完成，P2 為可隨階段整備。它們不代表現在已發生正式環境事故。

### 4.1 P0：時間政策與 M2 資源分類沒有單一口徑

M1 同時出現三種口徑：

- README 補充規則：當天 08:00–22:00。
- PLAN §1.6：提前窗口、最多四小時、完整開放時可跨午夜。
- 現行 `validate_period()`：未來、整點、同日、配置預設七日窗口，再查完整開放區間。

PLAN §2.2 已知道矛盾，但 T08/T09 不能在未決時直接採用 §1.6。建議把可約日期、每日邊界、午夜終點、`now == start_at` 等寫成一張已確認政策表，搜尋、建立、前端與測試共用。

此外，[M2 需求 §1–3](../m2-requirements.md) 已記錄本階段兩種教室開放模式互斥，且 M2 只允許整點；PLAN §5.4 用 09:30–11:30 示例，§8.2 要求 M2 非整點交集。兩者需區分「資源核心能計算任意區間」和「M2 業務允許提交什麼」。不能為了符合 PLAN 範例擅改 M2。

目前 Room 沒有預約模式欄位，M1 搜尋與建立也無法按模式排除僅供 M2 的教室。若沿用 M2 討論結果，須由公共資源負責人評審模式語義、遷移、舊教室初始值與變更影響；M1 接入篩選。仍保留來源重疊防護及 M2 真實寫回，不因列表隔離就刪除整合驗收。

既有 `occupy_room()` 還要求申請人為 TEACHER、操作者具有全域 `m2:approve`，而 M2 新需求允許所有有效身分提出申請，未來來源 HTTP 又使用服務主體。這是公共資源接入的相容工作，不能直接把現有函式包成 HTTP 就視為完成，也不能由 M1 代改 M2 申請資格。

### 4.2 P0：新 M1 權限與舊資源入口不一致

可重現的接入差異：

1. 主體只有 `m1:reservation:create`，且有合法學生身分和匹配範圍。
2. `require_student_for_room()` 通過。
3. `reserve_seat()` 先要求舊的 GLOBAL `m1:create`，立即回 403，尚未存取資料庫。

本輪分別以 GLOBAL 與 ROOM 範圍重現。預設 USER 同時有新舊權限，因此既有測試正常，不會暴露此差異。`release_source()` 同樣要求舊 GLOBAL `m1:cancel`；自動逾時、維修取消與正常結束也不能假借學生操作權。

後續需在 D 公共契約中明確：使用者與內部業務處理器如何呼叫資源、哪一層負責動作／範圍／所有權、SYSTEM／SERVICE 如何審計。不應用給所有學生補全域舊權限、偽造管理員主體或直接寫資源表來繞過。

### 4.3 P0：T06 預設要「復用」的公共設施實際不存在

PLAN §4.4 說復用 `d_outbox_events`，但目前 metadata、模型與遷移均無該表；也沒有資源操作記錄或可透過管理 API 更新的 M1 參數儲存。`booking_max_hours`、`booking_window_days` 現在是環境配置類欄位。

通知目前是單張 `d_notifications`，不是 PLAN 表中的通知三表；審計是 `d_operation_logs`，不是另一套 `audit_logs`。T06 應明確列為公共增量工作，說清表、維護者、公開登記／領取／完成介面與狀態，而不是指示實作者 import 不存在的模組。

最小任務契約需包含：唯一事件鍵、處理器類型、可執行時間、業務版本、狀態、租約持有人／期限／令牌、重試次數、下次重試、錯誤分類與人工處理入口。業務逾時／釋放任務不得與外部投遞共用「六次後永久放棄」策略。

### 4.4 P1：錯誤回應與交易回滾會影響失敗記錄

現有 Db 對拋出的例外回滾整個請求交易。後續若採「寫入失敗簽到嘗試 → raise DomainError(422)」，嘗試會一起回滾，持久化限頻失效。

相同問題還涉及：

- 寫入資源衝突操作結果後回 409，結果卻被回滾，無法核對。
- 簽到入口補做 NO_SHOW 後回錯誤，狀態、釋放與違約被回滾。
- 想記錄拒絕操作的審計，但拒絕例外使記錄消失。

PLAN 要求了這些效果，尚未給出與現有交易依賴相容的完成方式。建議明確區分「需要提交的業務拒絕結果」與「必須回滾的故障」；前者可由 Service 回傳受控結果，Router 正常回傳相應 HTTP 狀態，讓既有 Db 完成提交。具體實作要經契約確認；不要在 Service 私自 commit 或另開 Session。

對資料庫故障、完全未認證等無法依賴同一交易落庫的事件，另定安全記錄與補記邊界，不承諾每個拒絕都能同庫原子保存。

### 4.5 P1：背景與服務主體的審計缺少表示方式

[OperationLog](../../backend/app/modules/audit/models.py) 的 `actor_id` 必填且外鍵指向使用者；沒有 actor_type、獨立服務主體關聯、request_id 或明確結果欄位。現有資源服務也直接取 `actor.user_id`。

這不足以直接支援 M1 Worker 或經 D 認證的 M2/M3 服務主體。M1 的 ReservationEvent 已有 SYSTEM／SERVICE，但不能替代公共審計。T06/T12 需協調增量審計契約，避免將服務 ID 當使用者 ID 或設定虛構學生操作者。

同時確認哪些審計隨業務交易追加，哪些跨進程提交需要去重／補記；同庫本地審計不必一律繞遠端隊列。

### 4.6 P1：維修策略不能等到上線後才接入

現行 `start_maintenance()` 明確只加限制，不取消已有預約。T04 的停用、縮短開放遇有效來源時回 409，這是目前的保守保護。

PLAN 已規劃維修免責取消／中斷，但 T09 引入真實預約後，如果維修仍走舊入口，會出現「新預約已阻擋，舊預約狀態還正常」的缺口。學生預約投入共享使用前，必須具備維修影響處理，或有經人工確認的階段運行限制。

處理器屬 M1，D 不應查寫 M1 私有表。需要設計在公開協作邊界中如何以同一 Session、房間鎖及交易完成資源限制和 M1 影響；只是新增 HTTP 路由，不會自動改變既有 M3 的同進程呼叫。

本輪不更改 M3；其後續呼叫方遷移、失敗補償及真實網路驗收由相關負責人協同。也不代替 M2 決定已批准活動遇維修如何處理。

### 4.7 P1：來源版本與模型仍需增量補齊

現有來源已能重複取得、精確釋放並拒絕已釋放來源重新激活；但這不等於 PLAN 的完整版本協議：

- 沒有來源 revision、操作鍵與請求摘要／結果儲存。
- 未知來源先釋放會返回找不到，未建立防止舊添加復活的墓碑。
- ResourceBlock 約束只接受 M1／M2／M3，不能直接寫 ADMIN 類型。
- `materialize_source()` 沒有填寫 `m1_reservation_id`；目前 typed 外鍵是可選，不能把「欄位存在」當作新預約自動綁定。

T07/T09 需透過公開資源入口傳遞並保存新預約 typed 關聯；保留既有歷史空關聯，不虛構舊預約。若管理員封閉用既有啟停／開放規則表達，就明確記錄此方案；若要來源化 ADMIN 限制，再單獨評審 schema，不能照 PLAN 表格直接插入。

M2 整室來源對新增座位仍具權威限制；新增明細補算是追溯／投影工作，不能因明細缺失就放行。禁止再建第二套 `d_resource_holds` 事實來源。

### 4.8 P1：每日編碼與提醒的產品交付不只是一個 API

PLAN 有管理員查碼／輪換介面，但還需落實「誰在教室展示、用哪個受控頁、何時刷新、午夜失效、斷線怎麼提示」。不必新增硬體門禁，但要提供能實際展示的頁面或可驗證部署方式。

T10 應補 `m1:checkin_code:rotate` 或明確指定既有維護權限；目前 PLAN 權限表只有 read，不能把讀碼權當作改碼權。

T11 應把提醒有效窗寫成具體區間，而不是只寫「有效窗口」：前提醒最晚何時可投遞、+10 提醒是否在 +15 失效、遲建立或重啟後哪些必須抑制、最終違約通知如何去重。站內送達與外部推送的失敗／過期語義也要分清。

目前 D 站內通知失敗會讓呼叫方交易回滾。對 M1 必要釋放，應先同交易保存狀態與可重試通知任務，再由投遞器處理通知故障；這是 M1 新接入方式，不要求改寫既有 M3 通知政策。

### 4.9 P1：公共配置與角色管理仍有課程驗收缺口

目前 D 能分配／撤銷五種固定角色的範圍授權，權限映射由資料庫讀取；這不等於管理員能新增角色或配置角色權限。[UserRole](../../backend/app/modules/auth/models.py) 的 CHECK 及 [RoleGrantInput](../../backend/app/modules/auth/schemas.py) 都限定五種角色，沒有角色／權限設定 HTTP 入口。本輪以新角色 `OPS_ADMIN` 輸入重現 schema 拒絕。

任務書附件一的配置管理應列入 D 依賴追蹤與負責人工作包。M1 可註冊自己的動作並接入統一配置；不能為滿足驗收在 M1 私建角色體系。T13 的最大時長等參數也需明確儲存、白名單、單位、版本及生效時間，不能只改環境變數卻宣稱已完成線上配置。

### 4.10 P2：主資料版本、統計與效能需明確界線

- 管理輸入目前沒有 expected_version。`resource_version` 用於投影失效，不能阻止兩個管理員互相覆蓋更新；PLAN 中的期望版本屬後續能力。
- PLAN 說院系政策改變不追溯取消，現行 save_room 遇有效來源仍會對院系變更回 409；這是階段差異，T13 需明確轉換。
- `availability()` 會鎖房間並按座位 × 24 小時重建投影；M1 跨房間搜尋不宜簡單逐室呼叫，否則查詢本身增加寫鎖等待。先量測資料量、查詢計畫及延遲，再優化，不預先加入 Redis。
- 「實際分鐘」需依計畫時間裁剪，提早簽到不應讓使用兌現率超過 100%；完成任務延遲不應把 Worker 執行時間當作實際使用終點。
- 需確定統計日期、取消是否納入計畫分母、跨日切分與零分母。使用兌現率不能直接稱為全校資源利用率。
- 系統長時間停機後，已過結束時間但狀態未完成的預約，不能只依舊狀態機械判成維修中斷；需按有效時間補正並測試。
