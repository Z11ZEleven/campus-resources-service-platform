## 1. 基线核对与方案选择

原计划的“没有业务工程”描述属于历史分析，不能作为本轮代码事实。当前已有公共 D、M3、Vue 前端、MySQL 迁移、种子和 CI。

| 方案 | 收益 | 成本和结论 |
| --- | --- | --- |
| 沿用现有公共层并兼容扩充 | 复用 D 身份、资源入口、事务和 M3；维护同一技术基线 | 需要统一 D 契约和追加迁移；用户已确认采用 |
| 按旧计划重建 UUID、DATETIME(6) 和 JavaScript 工程 | 接近旧规划字面设计 | 影响已实现的所有模块及历史数据，不采用 |
| 在 M1 内另建认证、角色和资源表 | 可绕开 D 交付依赖 | 违反统一身份、权限和主数据边界，不采用 |

本轮统一 Vue 3 + TypeScript + Vite、Python/FastAPI、同步 SQLAlchemy Session、Alembic、MySQL 8.4。主外键使用 BIGINT UNSIGNED，HTTP ID 使用十进制字符串；数据库时间使用 UTC DATETIME(3)，业务日期按 Asia/Shanghai 解释。

公共目录继续采用 `app/modules/auth`、`resources`、`audit`、`notifications`，不新建重复的 `modules/d`。M1 私有模型放在 `app/modules/m1`。保留历史迁移，新增版本沿当前 `0003_m3_extensions` 链演进。

## 3. T02：复用工程并补齐可观测性

已有能力包括应用入口、事务型 Db 依赖、配置校验、`/health`、`/ready`、Vue 同源开发代理、依赖锁文件和 GitHub Actions。本轮扩展现有入口。

- 请求 ID 由服务端生成，响应头与错误体均返回同一个关联标识；处理异常和数据库提交失败时仍保留该标识。
- 保留客户端已使用的 `detail.code` / `detail.message` 结构；字段校验错误也提供可消费的字段详情，不回传输入中的密码或令牌。
- 未捕获异常返回通用错误；日志仅记录必要的关联标识和异常类别，不记录凭据、请求体或 SQL 参数。
- `/health` 仅表示进程可响应，`/ready` 真实探测数据库；不可达返回 503，不能据此声称预约业务完成。
- CI 继续使用真实 MySQL 8.4、`pytest --require-mysql`、Ruff 和前端生产构建；增加本轮测试入口和前端行为检查。
- 配置示例仅提供占位值；文档给出实际验证的安装、迁移、启动和检查命令。

验收：前后端启动、数据库可连接、断开数据库时 readiness 失败；成功、字段错误、拒绝、未捕获异常均有请求 ID；错误响应及日志不泄露虚构测试密码或令牌。

## 4. T03：扩展统一 D 身份与授权

当前 D 使用单身份、无服务端会话的 JWT 和固定角色权限映射，未满足原计划的多身份、可撤销会话和资源范围授权。所有补充仍位于统一 D auth 子域，M1 只使用公开依赖。

### 4.1 会话与身份

- 增加服务端会话记录，只保存随机凭据摘要、用户、所选身份、到期/撤销状态和必要时间。
- 浏览器使用 HttpOnly Cookie；生产 Secure、SameSite 和同源部署；变更请求执行 CSRF 校验。
- 在共同评审的迁移说明中明确旧 JWT 的失效和客户端切换步骤；不能保留绕过服务端会话的静默认证路径。
- 有效身份列表和身份切换均由 D 提供；校验所选身份属于当前用户且有效；身份类型、院系和角色不信任客户端输入。
- 用户停用、身份停用、角色撤销及会话撤销对下一次请求生效；退出和刷新页面恢复身份均有前端行为验证。

### 4.2 统一 RBAC 与范围

- 在 D 中登记权限、角色权限、角色授权及授权范围，M1 注册自身动作，不另建权限体系。
- 单条有效角色授权必须同时满足动作和资源范围；不能组合 A 角色的动作与 B 角色的范围越权。
- 查询先在 SQL 中施加范围再统计、分页；院系隔离使用所选的有效身份；SYS_ADMIN 不隐式获得业务权限。
- 明确现有角色授权的迁移与种子策略，不静默扩大现有成员权限；重复种子不恢复被撤销授权。
- 后续 M1 的本人所有权检查位于 M1 公开权限适配；T03 不提前实现预约路由。

### 4.3 服务主体

- D 统一维护服务主体、凭据摘要、所属模块和资源授权；凭据只从部署配置读取。
- 服务调用和浏览器主体分离；普通用户会话不能认证为服务主体；M2 主体不能写 M3 来源。
- 本轮交付认证与来源/范围校验能力；实际 M2/M3 资源写回路由及网络联调属于 T12/T16。

验收：未认证、会话过期/撤销、角色撤销、CSRF 缺失、跨院系、越界管理员、伪造/失效身份、动作与范围拼接均拒绝；错误服务凭据、模块不符和越界资源均拒绝；M3 既有业务测试继续通过。

## 6. T05：M1 模型、来源、占用与迁移

### 6.1 M1 私有模型

按照 PLAN_M1.md §4.3 建立五张业务表，但字段类型统一为现有 BIGINT / DATETIME(3)：

| 表 | 必须覆盖的约束和查询 |
| --- | --- |
| `m1_reservations` | 用户/身份及教室/座位组合归属；正时间区间；合法状态；用户与创建请求键唯一；请求摘要、设置/资源快照、签到/取消/结束时间与原因；用户历史及状态时段索引 |
| `m1_reservation_events` | 预约关联；事件、前后状态、操作者、请求关联和原因；按预约/时间/ID 查询；服务不暴露修改/删除入口 |
| `m1_violations` | 预约唯一；用户关联；类型、时间与原因；按用户时间查询 |
| `m1_room_checkin_codes` | 教室与校园日期唯一；nonce 与版本；不保存明文编码或密钥 |
| `m1_checkin_attempts` | 用户、预约、教室、时间和结果；持久化限频索引；不保存提交编码 |

本轮建立结构与读取 Repository，不实现创建预约、状态机、HMAC 编码或签到限频处理。

### 6.2 公共来源与占用

- 现有 `d_resource_blocks` 继续作为唯一来源事实表，不再创建一套含义重复的 `d_resource_holds`。
- 追加占用明细结构，与来源及教室—座位组合关联；M1 对应目标座位，M2 后续按时段展开，M3 仍以整室来源为权威限制。
- 迁移中处理已存在的 M1/M2 来源与关联座位，保留 M3 整室来源和全部释放记录；不能将迁移前来源当成不存在。
- M1 来源的业务外键/类型约束须采用可验证的关系设计，不能把多态 `source_id` 无条件外键指向 M1 表；也不能要求 M2/M3 私有表先存在。
- 资源表写入仍由 `resources/service.py` 负责；T07 才补齐完整统一裁决内核。
- 不新增独立 M1 配置系统；通过现有公共配置入口读取并记录快照。

验收：空库重放、从 0003 升级、带合成历史数据升级、再次 upgrade 和重复种子均通过；非法区间、错误座位归属和来源组合被数据库拒绝；模型与迁移一致，无循环建表依赖；M3 历史工单、通知和维修限制完整保留。
