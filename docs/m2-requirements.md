# M2 整教室预约与审批需求基线

状态：已根据课程任务书及 M2 负责人提供的团队讨论结果细化，待全组评审后成为正式基线。

本文件只描述 M2 已确认的业务规则、验收标准和依赖。尚未确认的实现细节明确标为“待定”或“建议”，不视为团队共识。

## 1. 范围

M2 负责整教室预约申请、两级审批、申请人撤回、审批超时自动撤销，以及最终批准后向资源维护方申请整教室占用。

本阶段不包含以下能力：

- 同一教室同时支持 M1 个人预约和 M2 整教室预约；
- 临近使用日期仍无整教室申请时，临时向 M1 开放个人预约；
- 已批准申请的取消或改期；
- 自然语言业务代理附加项。

其中“临近两天仍无整教室申请则开放个人预约”保留为后续候选功能，有余量时再单独设计和评审。

## 2. 身份、角色与数据范围

1. 用户身份分为学生、教师和工作人员。
2. 身份与角色分离；同一用户可以拥有多个角色。
3. 所有已认证且账号、身份有效的用户均可用本人身份提交整教室申请。
4. 服务端从认证上下文确定申请人，不接受客户端通过任意用户 ID 代替他人提交。
5. 审批角色至少包括院系管理员、校级管理员和教室管理员。
6. 审批授权同时检查角色和数据范围，不能只检查角色名称。
7. 院系归属教室的一级审批由具有对应院系范围的院系管理员处理。
8. 校级归属教室的一级审批由具有对应校级范围的校级管理员处理。
9. 二级审批由具有对应教室管理范围的教室管理员处理。
10. 申请人不得审批自己的申请，即使其同时拥有相应审批角色。

前端可以隐藏无权操作的入口，但服务端必须独立执行上述检查。

## 3. 教室范围与申请时间

1. 当前阶段教室开放模式互斥：面向 M1 的个人座位预约，或仅面向 M2 的整教室预约。
2. M2 申请只能选择当前有效且开放模式为“仅整教室预约”的教室。
3. 教室每日开放时间为 08:00 至 22:00，申请时段必须完全落在该范围内。
4. 申请开始和结束时间必须为整点。
5. 单次申请最短 1 小时、最长 4 小时。
6. 申请不得跨自然日。
7. 提交时，使用日期至少是提交日期之后的第二个自然日。
8. 所有业务时间按项目统一时区处理；当前建议使用 `Asia/Shanghai`，须在架构评审时确认。

“提前两个自然日”按本地日期计算。例如 10 月 21 日任意时刻提交，最早可申请 10 月 23 日 08:00 开始的时段。

时间区间统一使用左闭右开语义 `[start_at, end_at)`，因此 `[09:00, 10:00)` 与 `[10:00, 11:00)` 不冲突。

## 4. 申请信息

申请至少记录：

- 申请人用户及本次使用的身份；
- 目标教室；
- 使用开始和结束时间；
- 申请理由；
- 当前状态和审批层级；
- 当前审批步骤截止时间；
- 提交、审批、撤回、驳回、超时及最终批准等关键时间；
- 资源占用同步状态及并发控制版本。

是否需要人数、联系方式、附件等字段尚未确认，加入前必须补充业务目的、数据最小化要求和验收标准。

## 5. 两级审批

### 5.1 一级审批

一级审批由教室归属决定：

- 院系教室：对应院系管理员审批；
- 校级教室：对应校级管理员审批。

一级审批主要检查申请人身份和申请理由是否符合要求。通过后创建二级审批步骤；驳回时必须填写理由。

### 5.2 二级审批

二级审批由对应教室管理员处理，确认教室在申请时段能否支持整教室使用。

二级审批选择通过时，系统必须先通过公开接口原子地取得整教室资源占用。资源占用成功后申请才能进入“已批准”；资源冲突时自动驳回，并记录明确原因。

### 5.3 审批期限

每一级审批期限为一个自然日。当前按以下可执行口径实现：审批步骤创建后的下一自然日 23:59:59 截止，并以项目统一时区计算。

无论审批步骤的自然日截止时间为何，只要申请开始时间先到达且审批仍未完成，就立即自动撤销申请。

系统需要在申请开始时间临近而审批尚未完成时提醒当前审批管理员。具体提前量尚未由团队确认，应做成配置项；首版建议默认提前 24 小时，并在实现前由团队评审。

## 6. 状态机

首版业务状态如下：

```text
待一级审批
  ├─ 一级通过 → 待二级审批
  ├─ 一级驳回 → 已驳回
  ├─ 申请人撤回 → 已撤回
  └─ 超时或到达使用时间 → 已自动撤销

待二级审批
  ├─ 资源占用成功 → 已批准
  ├─ 二级驳回 → 已驳回
  ├─ 资源冲突 → 已驳回
  ├─ 申请人撤回 → 已撤回
  └─ 超时或到达使用时间 → 已自动撤销
```

建议在实现中使用独立的资源同步状态或短暂的“资源确认中”内部状态，避免把“已经发起资源请求”错误表示为“已批准”。该内部状态是否暴露给前端由接口设计决定。

所有状态转换必须使用事务、条件更新或乐观锁保证并发安全。终态包括已批准、已驳回、已撤回和已自动撤销；终态不能再执行审批或撤回。

## 7. 申请人撤回

1. 申请人可在待一级审批或待二级审批时撤回本人申请。
2. 非申请人不能代为撤回。
3. 终态申请不能撤回。
4. 当前阶段待审批申请不预占资源，因此正常撤回不产生资源释放操作。
5. 撤回必须记录时间和操作者，并使尚未处理的审批任务失效。

## 8. 同时段申请和资源占用

待审批阶段不预占教室，因此允许同一教室、重叠时段存在多份待审批申请。

二级审批通过时由资源维护方执行最终冲突检查和原子占用：

1. 同一教室的重叠整教室占用最多一个成功。
2. 第一份成功占用的申请进入已批准。
3. 与其冲突的其他待审批申请自动驳回，原因写明“教室对应时段已被其他申请占用”。
4. 并发审批不能使用无锁的“先查询、后插入”作为唯一保护，必须有事务和数据库约束或等效的可验证并发控制。

## 9. M2 到资源维护方的集成

最终批准必须通过公开网络接口创建整教室限制，不得直接读写 M1 或其他模块的私有表。

资源限制至少包含：

- 来源模块 `M2`；
- 来源业务 ID，即 M2 申请 ID；
- 教室 ID；
- 生效开始和结束时间；
- 幂等键或业务版本；
- 当前状态。

资源调用要求：

1. 相同申请和版本的重复请求幂等。
2. 同一教室重叠占用通过统一并发控制判断。
3. 资源占用成功后 M2 才返回最终批准成功。
4. 资源冲突导致申请自动驳回并保存原因。
5. 网络或服务异常不能伪装成业务冲突或批准成功；重试和最终失败策略在接口设计阶段补充。
6. M2 来源必须可追溯到具体申请。
7. 将来释放 M2 来源时只能释放本申请的限制，不得影响 M1、M3、管理员或其他 M2 来源。

即使仅整教室预约的教室当前不出现在 M1 列表中，也必须创建来源化资源限制，以满足任务书的状态写回、追溯和真实跨模块调用要求。

## 10. 通知与审计

至少为以下事件生成通知或待投递记录：

- 进入一级审批；
- 进入二级审批；
- 临近申请开始但仍未完成审批；
- 申请批准；
- 申请驳回；
- 申请人撤回；
- 审批超时自动撤销。

审批、驳回、撤回、超时和资源同步结果必须记录操作者、时间、申请、原状态、目标状态和结果。不得记录密码、Token 或完整敏感请求。

具体通知渠道尚未确认。首版可以依赖公共通知服务的站内通知能力，但不能以普通开发日志冒充最终通知。

## 11. 验收标准

### 11.1 申请和时间规则

- 学生、教师和工作人员均可用本人有效身份提交申请。
- 客户端提交其他用户 ID 不能冒充申请人。
- 非整教室预约类型、停用或不在权限允许范围内的教室不能提交。
- 非整点、少于 1 小时、超过 4 小时、跨天或超出 08:00 至 22:00 的申请被拒绝。
- 未提前两个自然日的申请被拒绝，并验证月末、年末等日期边界。

### 11.2 权限和审批

- 院系管理员只能审批其院系范围内教室的一级申请。
- 校级管理员只能审批其校级范围内教室的一级申请。
- 教室管理员只能审批其管理教室的二级申请。
- 申请人不能审批自己的申请。
- 一级通过后只进入二级，不能直接批准。
- 任一级驳回都必须有非空理由，驳回后不能继续审批。
- 越权操作在服务端被拒绝并记录必要审计。

### 11.3 撤回和超时

- 申请人可撤回任一级待审批申请，其他用户不能代为撤回。
- 终态申请不能撤回。
- 每一级在自然日截止时仍未审批则自动撤销。
- 使用开始时间到达时仍未完成审批则自动撤销。
- 定时任务重复执行或服务重启补执行不会重复转换状态或重复产生业务影响。
- 人工审批、撤回和超时任务并发时最多一个状态转换成功。

### 11.4 资源和并发

- 二级通过时通过真实网络公开接口创建 M2 整教室占用。
- 资源占用成功前申请不进入已批准。
- 同一教室重叠时段最多一份申请批准成功，其余冲突申请自动驳回并记录原因。
- 重复资源请求不产生重复限制。
- M2 占用能追溯到具体申请和有效时段。
- 移除一个来源时不会误释放其他来源限制。
- 至少执行一次真实并发测试，并通过故意破坏并发保护验证测试会失败。

## 12. 依赖与待评审项

M2 依赖公共层提供：

- 用户、有效身份、多角色和数据范围；
- 教室归属、开放模式、启停和开放时间；
- 统一资源占用公开接口；
- 通知服务和操作审计。

进入实现前还需在状态机和接口评审中确认：

1. 统一时区是否确定为 `Asia/Shanghai`。
2. 临近开始时间提醒的默认提前量。
3. 网络异常时资源确认的重试、恢复和人工处理策略。
4. M2 业务表、公共表及跨 schema 外键的迁移顺序。
5. 具体通知渠道。
