# ADR-0001：技术选型

- 状态：本轮用户确认的实现基线；组内批准待记录
- 日期：2026-10-19
- 决策参与人：待填写

## 背景

约六人开发预约、审批、报修平台，需支持权限、事务、迁移、测试及部署；团队倾向使用 Python。

## 候选

1. Python + FastAPI，前端独立：接口边界清楚，但后台管理、权限和任务调度需明确集成方案。
2. Python + Django，可配独立 API：有内置管理和认证基础，但仍需实现业务权限及审批规则。
3. 团队提出的其他方案：待补充。

历史曾提出 Vue、PostgreSQL 等候选。2026-10-22 用户明确确认沿用当前 Vue 3 + TypeScript、FastAPI、MySQL 8.4、BIGINT UNSIGNED、UTC DATETIME(3)，并授权直接实施 M1 T01–T05；该授权不是全组批准记录。

## 比较依据

成员熟悉度、第一轮实现成本、权限与事务、测试迁移支持、模块网络调用、维护与部署复杂度。

## 最终决策与后果

## 本轮实施选择（2026-10-22）

采用现有 Vue 3 + TypeScript + Vite、Python 3.12 + FastAPI、同步 SQLAlchemy 2.0 + PyMySQL、MySQL 8.4、Alembic、pytest、GitHub Actions。精确依赖沿用仓库锁文件。HTTP Db 依赖在响应前提交，服务仅 flush；READ COMMITTED，资源变更先锁房间。

候选一是兼容扩充现有 D 与 M3，避免迁移已交付模块，采用；候选二是按旧 M1 计划改用 JavaScript/UUID/DATETIME(6)，影响全模块和已有数据，放弃；候选三是在 M1 重建认证及资源系统，违反模块边界，放弃。

代价是公共身份及资源结构必须追加统一迁移，前后端会话契约需一起切换，原无服务端记录的 JWT 不再作为受保护 HTTP 的有效会话。数据库迁移、旧数据保留、M3 回归均列入验收。

本轮用户授权先实现可评审提案；人员确认、共同评审与人工验收仍待实际记录，合并和生产发布按现有规则执行。方案与验收见 [M1 T01–T05](../m1/t01-t05-design.md)。
