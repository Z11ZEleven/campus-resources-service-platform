# M1 交付实施计划

用户已授权根据 T11–T17 及验收发现继续实施。执行方式：当前会话持续实现，保留已有工作区修改。

## 设计与约束

沿用单库、同步事务和公开资源服务。房间锁先于业务行锁；通知通过 Outbox，与必要状态变更解耦。D 不读写业务私表，资源变更的 M1 影响由 M1 公开处理器承接。现有同进程 M3 流程首先补正确性；网络链路另以真实进程验证，不将 TestClient 作为网络证据。

没有 M2 业务模块；不擅自代替其他组设计审批系统。其交付依赖必须如实记录。人工评审、共享环境权限和发布审批不由 AI 代签。

## 步骤和验收

1. 创建任务分支、独立 MySQL 8.4 容器及显式 `campus_delivery_test` 库。完整回归，记录真实失败。
2. `tests/test_m1_delivery.py` 先复现真实 M3 开始维修漏免责、开放时间缩短漏处理。修复接入，在同一事务内释放个人来源、保留实际结束与事件。保留其他模块来源的冲突保护。
3. 资源操作表追加版本化迁移，将幂等键隔离到服务主体；查询也按主体过滤。不同服务同键可独立使用，同服务异载荷拒绝。锁后重验服务凭据。
4. 定时测试覆盖三个时点、重复执行、失效提醒、违约与完成，补并发/重试行为。以完整 MySQL 回归和关键失败→通过证据验收。
5. 学生/管理前端补行为测试与真实浏览器流程；确认时间、重复提交、权限、取消和复用。
6. 补生产构建镜像、同源代理、独立 Worker、一次性迁移与 CI 检查，文档写明启动版本与前向修复/回退限制。仅将实际验证的范围标为通过。

最终检查：Ruff、完整 MySQL pytest、Alembic 模型一致性、前端类型与构建、前端行为/E2E、真实 HTTP、git diff --check。结果写入 docs/m1/verification.md，未完成项保留。
