### 1.2 核心目标

M1 为学生提供“查找座位 → 立即预约成功 → 到场签到 → 使用结束”的完整流程，同时支持取消、历史查询、历史复用和违约记录。

“立即生效”解释为：**资源事务提交成功后，预约即成立，无需审批；不表示使用时段立即开始。**

完整预约条件为：

```text
统一认证与动作授权通过
且所选身份、院系与资源范围符合规则
且资源有效、启用并完整覆盖开放区间
且满足 M1 预约参数
且不存在冲突的个人预约、整室占用、维修或管理员限制
```

搜索与提交共享判定规则，但搜索只提供查询时的结果；提交必须重新检查并原子裁决。

### 1.5 状态与主要流程

建议采用以下 M1 状态：

| 当前状态 | 触发 | 后续状态 | 资源及记录处理 |
|---|---|---|---|
| 无 | 预约事务成功 | `RESERVED` | 创建个人来源和占用明细 |
| `RESERVED` | 合法签到 | `CHECKED_IN` | 保存签到时间，停止未签到提醒 |
| `RESERVED` | 开始前本人取消 | `CANCELLED` | 精确释放，不计违约 |
| `RESERVED` | 到达开始后 15 分钟仍未签到 | `NO_SHOW` | 释放、违约、通知同一业务事务登记 |
| `CHECKED_IN` | 到达预约结束时间 | `COMPLETED` | 保存实际结束时间，结束使用 |
| `RESERVED` | 维修影响 | `CANCELLED` | 原因为系统维修，免责并通知 |
| `CHECKED_IN` | 维修影响 | `INTERRUPTED` | 保存中断时间和实际使用时长，免责并通知 |

终态不允许普通接口重新激活；再次预约必须创建新预约。

## 3. 技术方案与架构设计

### 3.1 推荐技术路线

| 层次 | 推荐 |
|---|---|
| 前端 | Vue 3、TypeScript、Vite、Element Plus、Vue Router |
| 后端 | Python 3.12、FastAPI、Pydantic 2 |
| 数据访问 | SQLAlchemy 2，同步 Session、PyMySQL |
| 数据库 | MySQL 8.4、InnoDB、`utf8mb4` |
| 迁移 | Alembic，仓库统一迁移历史 |
| 后台处理 | 独立 Python Worker，数据库持久化任务 |
| 测试 | pytest、HTTPX、真实 MySQL；Vitest、Vue Test Utils、Playwright |
| 部署 | Docker Compose、同源反向代理、GitHub Actions |

具体补丁版本在基础工程任务中解析、兼容验证后写入锁文件与镜像固定版本，不使用浮动 `latest`。

SQLAlchemy 官方提供 MySQL/PyMySQL、MySQL JSON 与微秒时间类型支持，可沿用仓库候选 ORM，无需增加第二套数据访问方案。[SQLAlchemy MySQL 文档](https://docs.sqlalchemy.org/en/20/dialects/mysql.html)

### 3.2 方案比较

| 方案 | 优点 | 代价 | 结论 |
|---|---|---|---|
| M1 与 D 空间子域同服务、同事务；M2/M3 经 HTTP 调用 | 预约和资源占用原子提交；不需要分布式预约状态机 | 同室写入串行，需要统一资源入口 | **采用** |
| 独立 D 资源服务 | 部署边界更独立 | M1 需要资源协调状态、补偿和额外故障恢复 | 不作为首版 |
| Redis 锁、消息代理和分布式协调 | 可扩展性较高 | 新增基础设施与一致性负担，当前没有基础 | 不引入 |

前端沿用现有 TypeScript 工程及统一请求客户端，不为 M1 另建 JavaScript 基线。

### 3.3 模块组织与调用边界

建议新增以下目录，为原规划的目标结构；本轮沿用现有目录，不重复创建公共层：

| 建议目录 | 职责 |
|---|---|
| [backend/app/core](../backend/app/core) | 配置、数据库、异常、日志、请求关联标识 |
| [backend/app/modules/m1](../backend/app/modules/m1) | 预约、签到、违约、使用统计、M1 任务 |
| backend/app/modules/d（规划路径 `backend/app/modules/d`） | 统一身份、空间资源、通知、审计子域 |
| backend/migrations（规划路径 `backend/migrations`） | 统一版本化迁移 |
| [backend/tests](../backend/tests) | 单元、MySQL 集成及网络契约测试 |
| frontend/src/views/m1（规划路径 `frontend/src/views/m1`） | M1 学生和管理页面 |

每个业务子域采用 `router → service → repository` 分层，Pydantic Schema 与 ORM Model 分开。

- Router：解析输入、接入认证、映射响应。
- Service：业务条件、授权复核、事务和状态转换。
- Repository：查询与持久化，不自行提交业务事务。
- D 空间 Service：主数据、开放区间、来源、占用及资源版本的唯一维护入口。
- M1 Service：预约状态、签到、违约及业务通知触发的唯一维护入口。

M1 调用 D 空间的公开 Python Service 接口并共享事务，不直接操作 D 私有 Repository。M2/M3 调用公开 HTTP 接口，不直接写资源表。

真实网络验收必须由实际 M2 或 M3 服务发起，HTTP 测试客户端只能作为较早阶段的接口验证，不能冒充完整模块链路。

### 3.4 并发与事务策略

首版使用**教室行锁**协调所有影响同室可用性的写入。

```text
开始事务
→ 锁定教室行
→ 必要时按 ID 升序锁定受影响预约
→ 重新检查权限、状态、开放区间和真实来源
→ 修改预约或资源来源、占用明细
→ 追加业务事件和持久化任务
→ 递增资源版本
→ 提交
```

预约、取消、签到、超时、维修、M2 占用、座位增减和开放规则变更遵循相同顺序。预约所属教室先做非锁定定位，锁定后再次确认，禁止先锁预约再等待教室。

使用 `READ COMMITTED`，避免等待教室锁后仍用旧快照检查冲突；关键检查使用事务内当前数据。`FOR UPDATE` 须在显式事务中使用，其锁在提交或回滚时释放。[MySQL 锁定读取文档](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

重叠公式统一为：

```text
existing.start_at < requested.end_at
且 existing.end_at > requested.start_at
```

开放终点的限制按正无穷处理。

其他约束：

- 不在持有资源锁时发送通知或调用远程服务。
- 死锁只对可重试、具备幂等保护的完整事务重试，最多 3 次；耗尽返回可重试错误。
- `SKIP LOCKED` 只用于 Worker 领取任务，不用于跳过预约冲突。
- 不把普通唯一索引描述为时间范围互斥约束。
- 同教室不同座位也会短暂串行，这是首版以吞吐量换取简单可靠裁决的明确取舍。

| `d_resource_blocks`、`d_seat_allocations` | 来源台账和实际占用 | 同上 |
| `seat_status_summary` | 可重建的查询投影 | 同上；不是预约事实源 |
| `system_settings` | M1 参数，按键定义类型、单位和边界 | 公共配置接口维护 |
| 通知三表、`audit_logs`、`outbox_events` | 通知投递、审计、持久化任务 | D 对应子域 |

不为 M1 另建用户表、角色表、通知投递系统或公共审计表。

### 4.2 PostgreSQL 草案到 MySQL 的最小适配

| 草案设计 | MySQL 实施方案 | 影响 |
|---|---|---|
| `d.users`、`m1.reservations` 等 schema | 同数据库内使用 `d_users`、`m1_reservations` 等前缀 | 所有模块统一映射 |
| UUID 旧建议 | 沿用 `BIGINT UNSIGNED`；API 输出十进制 ID 字符串 | 避免全模块破坏性迁移 |
| `TIMESTAMPTZ` | UTC `DATETIME(3)`；应用负责 UTC 转换，连接时区固定 UTC | ORM 不得丢失时区语义 |
| `JSONB` | MySQL `JSON` | 查询表达式使用 ORM 方言 |
| 条件唯一索引 | 可空生成列加唯一索引 | 主要身份、有效授权等规则 |
| PostgreSQL 排斥约束 | 教室锁、事务内重叠检查、受控唯一写入口 | 必须用真实 MySQL 并发测试验证 |
| 跨 schema 外键 | 同库表前缀外键；跨模块私有业务单采用逻辑引用 | 避免要求 M2/M3 表先存在 |

`DATETIME` 不自动提供 PostgreSQL `TIMESTAMPTZ` 的等价语义，UTC 归一化必须由应用和测试保证。[MySQL 时间类型文档](https://dev.mysql.com/doc/refman/8.4/en/datetime.html)

条件唯一示例：主要身份生成列仅在 `is_primary = TRUE` 时返回 `user_id`，其余返回 `NULL`，再建立唯一索引。MySQL 唯一索引允许多个 `NULL`，可承载此约束。[MySQL 索引文档](https://dev.mysql.com/doc/refman/8.4/en/create-index.html)

其他适配要求：

- 保留 `d_resource_blocks` 中三个类型化业务来源字段及各自唯一约束。
- M1 预约外键可在预约表创建后补充；M2/M3 来源字段首版作为逻辑业务标识，不强制引用其私有表。
- 保留座位与教室组合归属校验，不用两个独立外键冒充“座位属于该教室”。
- 管理员来源采用来源记录自身 ID，不复用 M2/M3 身份。
- 所有这些变更同步更新公共表设计、ADR 和接口示例。

### 4.3 M1 新增业务表

所有表统一具有 BIGINT UNSIGNED 主键和创建时间；可变表增加更新时间及版本。下面列出关键业务字段。

| 建议表 | 关键字段 | 约束、索引与用途 |
|---|---|---|
| `m1_reservations` | `user_id`、`identity_id`、`room_id`、`seat_id`、`start_at`、`end_at`、`status`、`checked_in_at`、`actual_end_at`、`cancelled_at`、`end_reason`、`settings_snapshot`、资源标签快照、创建幂等键及请求摘要 | `end_at > start_at`；座位归属约束；唯一 `(user_id, create_request_key)`；索引 `(user_id, created_at, id)`、`(room_id, status, start_at)`、`(status, start_at)`、`(status, end_at)` |
| `m1_reservation_events` | 预约 ID、事件类型、前后状态、操作者类型/ID、关联 ID、原因、必要详情 | 只追加；索引 `(reservation_id, created_at, id)`；与状态变化同事务 |
| `m1_violations` | 预约 ID、用户 ID、类型、发生时间、原因 | `reservation_id` 唯一，防止重复记违约；按用户和时间查询 |
| `m1_room_checkin_codes` | 教室 ID、校园日期、随机 nonce、版本 | 唯一 `(room_id, business_date)`；不保存明文编码或服务密钥 |
| `m1_checkin_attempts` | 用户 ID、预约 ID、教室 ID、尝试时间、结果 | 索引 `(user_id, room_id, attempted_at)`；不保存提交的编码；支持持久化限频 |

签到编码由环境密钥、教室、校园日期和 nonce 计算 HMAC，再截取为 8 位数字显示；编码生成与校验共用实现。密钥不进表、不进仓库。

失败尝试也须可靠登记；不能因业务返回“编码错误”而回滚尝试计数。

### 4.4 公共资源及任务表的必要扩展

**新增 `d_resource_operations`：**

保存服务主体、操作键、来源类型、来源业务 ID、请求摘要、响应状态、响应内容、关联 ID 和时间。

- 唯一 `(service_principal_id, operation_key)`。
- 支持超时后重试返回原结果。
- 同键不同载荷返回 `409 IDEMPOTENCY_KEY_REUSED`。
- 资源冲突结果可以提交为操作结果，但不写入有效占用。
- 暂时性内部错误回滚，允许相同操作键重试。
- 操作重放保证期建议为 180 天；已释放来源的最小版本墓碑不随操作记录清理。

**扩展通知契约和存储：**

- 消息增加有效截止时间、业务版本和失效校验所需关联。
- 投递状态增加 `CANCELLED`，用于取消、签到或过期造成的业务失效。
- D 在每次实际投递尝试前核验有效性；不只在入队时核验。
- 外部渠道已经接受的消息无法撤回；验收保证不发送在投递授权检查前已失效的提醒。

**复用 `d_outbox_events`：**

M1 的提醒、超时、完成任务及公共通知/审计提交均通过公开 Outbox 接口登记，不再新建第二张 M1 Outbox 表。业务处理器仍属于 M1。

### 4.5 来源、占用和汇总规则

- M1：一条预约来源、一条目标座位占用。
- M2：一条整室来源，为当前有效座位生成占用明细；整室来源本身是权威限制。
- M3：每张工单独立整室限制，不生成无限未来的座位明细。
- 同室允许多张维修工单叠加。
- 释放只变更对应来源和其明细，不覆盖其他来源。
- 自然到期不等于删除历史；有效性同时判断状态和时间。
- 汇总以资源版本标记新旧；缺失或过期时回退到真实计算，不能默认可预约。
- 首条业务链路可以直接查事实表；随后补汇总，始终不把汇总作为提交依据。

座位有历史记录后，不允许原地迁移到另一教室；采用注销旧座位、登记新座位的方式保持历史关系。

### 4.6 维修和主数据变更

本次确认的维修策略：

1. 在教室锁内写入维修限制。
2. 找出有效区间重叠的 M1 预约。
3. 未签到预约免责取消；已签到预约转为 `INTERRUPTED`。
4. 释放这些个人来源，保留原计划时间及业务事件。
5. 记录实际使用终点，登记通知和审计任务。
6. 同一事务提交后才向 M3 返回“限制已生效”。

未知维修终点按持续有效处理，因此可能取消预约窗口内全部未来预约。维修提前完成不自动复活这些预约。

M2 来源可以与维修限制并存。M1 不代替 M2 取消审批单；M2 对已有整室活动的处置属于双方集成契约，响应只提供必要影响计数和关联标识。

管理员关闭资源或缩短开放区间时，对受影响 M1 预约采用相同的免责取消/中断流程。仅修改院系开放政策时，不追溯取消既有预约；新预约使用新政策。

### 4.7 权限落地

统一认证与 RBAC 由 D 身份子域交付，M1 只接入公开依赖。

建议首版统一采用可撤销服务端会话：

- 浏览器使用 `HttpOnly`、`Secure`、`SameSite` Cookie。
- 修改请求检查 CSRF；生产同源部署。
- 每次请求读取当前用户、角色、授权有效期和资源范围；首版不缓存权限。
- 服务调用使用 D 统一管理的服务主体及凭据校验；凭据来自部署配置，服务主体绑定模块和资源范围。
- 普通用户会话不能调用内部资源接口。

建议动作权限：

| 权限标识 | 附加约束 |
|---|---|
| `m1:seat:search` | 有效身份及可见资源范围 |
| `m1:reservation:create` | 有效学生身份、院系政策、完整预约条件 |
| `m1:reservation:read_own` | 当前用户所有权 |
| `m1:reservation:cancel_own` | 所有权、状态及截止时间 |
| `m1:reservation:checkin` | 所有权、签到窗口及编码 |
| `m1:violation:read_own` | 当前用户所有权 |
| `m1:reservation:read_scoped` | 管理授权资源范围 |
| `m1:statistics:read` | 管理授权资源范围 |
| `m1:settings:write` | 全局范围，不因局部管理权限放行 |
| `m1:checkin_code:read` | 教室范围，不向学生开放 |
| `d:space:read/write` | 对应资源范围 |
| `d:resource:m2_write`、`d:resource:m3_write` | 对应服务主体及来源类型 |

具体校验必须满足：

- 客户端不能指定可信 `user_id`、角色、部门、状态或操作者。
- `identity_id` 可作为选择参数，但服务端验证其属于当前用户且有效。
- 同一条有效角色授权必须同时具备动作权限和匹配资源范围，不能拼接不同角色的权限与范围形成越权。
- 本人历史、取消、签到不能机械套用“当前是否还能新预约该院系教室”；分别按业务规则检查。
- 管理查询在 SQL 查询中施加范围，再分页和聚合，防止总数、统计和详情泄漏。
- 不可见业务记录统一返回 `404`；缺动作权限返回 `403`。
- 权限状态不可确认时返回依赖错误，不默认放行。

### 4.8 迁移与兼容策略

建议统一迁移顺序：

1. D 身份及角色权限表，由 D 身份负责人维护。
2. D 主数据和开放规则、公共配置。
3. M1 业务表、来源台账、占用、资源操作记录。
4. M1 外键及公共表兼容适配。
5. D 通知、审计和 Outbox，由相关负责人维护。
6. 来源汇总及性能索引。

不为 M2/M3 预先创建空的私有业务表。

验证要求：

- 空库执行到最新版本。
- 在已经升级的库再次执行升级，无重复结构或数据。
- 从前一版本及有合成业务数据的状态升级。
- 重复执行种子脚本不产生重复身份、资源、权限或模板。
- MySQL DDL 失败后按实际结构和版本表诊断，不假定能整体事务回滚。
- 有真实历史数据时先备份、检查和验证转换；不重建共享数据库。
- 发布优先采用新增兼容结构和前向修复；破坏性降级、删表或删列须人工审批。

## 5. API 与前后端整合设计

以下接口全部为**建议新增**，不是现有 API。

### 5.1 通用约定

- 对外前缀：`/api/v1`。
- JSON 使用 `snake_case`，不同时兼容两套字段风格。
- 资源/业务 ID 使用 BIGINT 的十进制字符串；时间使用带偏移量 ISO 8601，响应统一 UTC。
- 输入禁止额外字段，避免批量赋值修改状态或所有者。
- 列表默认 20 条、最大 100 条，稳定按时间与 ID 排序。
- 统一错误体：

```json
{
  "error": {
    "code": "RESOURCE_CONFLICT",
    "message": "该时段已不可预约",
    "request_id": "UUID",
    "details": {
      "conflict_type": "ROOM_OCCUPANCY"
    }
  }
}
```

不返回 SQL、堆栈、凭据或其他学生身份信息。

| 状态码 | 语义 |
|---|---|
| `401` | 未登录、失效会话或无效服务凭据 |
| `403` | 无动作权限或服务来源权限 |
| `404` | 不存在或当前主体不可见 |
| `409` | 资源冲突、非法状态、过期版本、同键异载荷 |
| `422` | 字段、时间、身份选择或编码校验不通过 |
| `429` | 签到尝试超限 |
| `503` | 授权或必要依赖不可用、事务重试耗尽 |

### 5.2 学生 API

| 方法与路径 | 输入 | 输出及规则 |
|---|---|---|
| `GET /m1/seats` | `identity_id`、`start_at`、`end_at`、可选教室和插座条件、分页 | 可预约座位、位置、属性、查询时资源版本；不含预约人信息 |
| `POST /m1/reservations` | `identity_id`、`seat_id`、开始结束时间；必需 `Idempotency-Key` | `201`，预约 ID、状态、时段、签到窗口、版本 |
| `GET /m1/reservations` | 状态、日期、分页 | 仅本人；覆盖当前和历史 |
| `GET /m1/reservations/{id}` | 路径 ID | 本人详情、业务事件及 `allowed_actions` |
| `POST /m1/reservations/{id}/cancel` | 无所有者或状态字段 | 首次成功取消；重复取消返回已有结果；其他终态返回冲突 |
| `POST /m1/reservations/{id}/check-in` | `code` | 签到结果和服务端时间；已签到重复提交不重复记账 |
| `GET /m1/violations` | 日期、分页 | 仅本人违约记录 |

创建请求：

```json
{
  "identity_id": "123",
  "seat_id": "123",
  "start_at": "2026-11-01T09:00:00+08:00",
  "end_at": "2026-11-01T11:00:00+08:00"
}
```

创建幂等键按用户隔离：

- 同键同请求返回原预约结果，不重复生成任务。
- 同键不同请求返回 `409`。
- 资源冲突未创建预约；用户重新确认后使用新键提交。
- 前端因超时重试时保留原键；用户修改座位或时间后生成新键。

历史复用不增加独立写接口，直接调用普通预约创建流程。

### 5.3 管理与公共资源 API

| 方法与路径 | 功能与约束 |
|---|---|
| `GET /m1/admin/reservations` | 授权范围内查询预约 |
| `GET /m1/admin/statistics` | 授权范围内按日期、教室聚合 |
| `GET /m1/admin/settings` | 读取 M1 可见参数 |
| `PATCH /m1/admin/settings` | 白名单键、值校验、期望版本、全局授权和审计 |
| `GET /m1/admin/rooms/{id}/check-in-code` | 当日编码与过期时间；教室范围授权，禁止缓存 |
| `POST /m1/admin/rooms/{id}/check-in-code/rotate` | 更新当日 nonce，立即使旧码失效并审计 |
| `GET /spaces/rooms`、`GET /spaces/rooms/{id}/seats` | D 统一资源目录，按权限过滤 |
| `POST /spaces/rooms`、`PATCH /spaces/rooms/{id}` | 登记及修改教室，采用期望版本 |
| `POST /spaces/rooms/{id}/seats`、`PATCH /spaces/seats/{id}` | 座位登记、属性修改及软注销 |
| `GET /spaces/rooms/{id}/opening-rules` | 读取周期及特殊开放规则 |

不提供普通用户物理删除资源的接口。管理端变更影响已有预约时，响应返回处理数量和关联 ID。

### 5.4 M2/M3 资源接口

统一接口：

```text
PUT /api/v1/internal/resource-holds/{source_type}/{source_id}
GET /api/v1/internal/resource-holds/{source_type}/{source_id}
GET /api/v1/internal/resource-operations/{operation_key}
```

`source_type` 首版仅允许 `M2`、`M3`；路径不允许普通客户端写入 `M1` 或 `ADMIN`。

M2 请求：

```json
{
  "room_id": "123",
  "active": true,
  "revision": 1,
  "start_at": "2026-11-01T09:30:00+08:00",
  "end_at": "2026-11-01T11:30:00+08:00",
  "reason": "整教室预约"
}
```

M3 请求：

```json
{
  "room_id": "123",
  "active": true,
  "revision": 1,
  "reason": "教室维修"
}
```

共同要求：

- 请求携带服务凭据及 `Idempotency-Key`。
- M2 必须提供有限时段；M3 首次激活的起点由服务端确定，终点未知。
- 释放使用相同来源 ID、`active:false` 和更高 revision。
- M2 释放携带原房间和时段；M3 释放携带原房间。
- 来源绑定房间后不可换房间；新业务使用新来源 ID。
- 成功响应包含来源状态、已接受 revision、资源版本、操作结果及必要影响计数。
- 成功意味着数据库已经提交、预约判断已经受限，不能只代表“请求已入队”。

版本规则：

| 场景 | 明确处理 |
|---|---|
| 同操作键、同请求 | 返回原结果 |
| 同操作键、不同请求 | `409 IDEMPOTENCY_KEY_REUSED` |
| 同来源、同 revision、相同状态与载荷 | 返回已应用 |
| 同 revision、不同载荷 | `409 REVISION_CONFLICT` |
| 低 revision | `409 STALE_REVISION`，返回当前 revision |
| 较高 revision | 校验后应用；允许跳号，不依赖中间事件 |
| 未知来源先收到释放 | 创建已释放墓碑，保存 revision |
| 已释放后到达旧激活 | 拒绝，不复活 |
| 已释放后要求重新激活同来源 | `409 SOURCE_TERMINAL`；首版同来源释放为终止 |
| 激活因资源冲突失败 | 不推进来源版本；原操作结果仍可核对 |
| 冲突解决后重新尝试 | 使用新操作键；未应用的来源 revision 可以重新评估 |

M2 获得资源成功前不得显示最终“预订成功”。M1 负责返回可靠结果；M2 自己维护审批与资源协调状态。

### 5.5 通知与后台任务

预约创建时，在同一事务登记：

- 开始前 15 分钟提醒；
- 开始后 10 分钟未签到提醒；
- 开始后 15 分钟未签到处理；
- 预约结束处理。

建议 Worker 每 30 秒扫描一次：

- 提醒只有处于合法状态及有效投递窗口时才发送。
- 创建预约时已经错过预约前提醒窗口，则不补发该提醒。
- 重启后超过 15 分钟的未签到预约直接处理 `NO_SHOW`，不连续补发旧的两次提醒。
- 签到和超时竞争时，以加锁后服务端时间裁决；达到 `start_at + 15 分钟` 即不能签到。
- 即使 Worker 延迟，签到入口也执行相同到期判断。
- `NO_SHOW`、来源释放、违约及通知任务在一个事务完成。
- 业务定时任务持续重试并告警；不能因达到通知重试次数而永久放弃资源释放。
- 外部通知/审计提交采用租约、退避和最多 6 次自动尝试，耗尽进入人工处理。

D 通知接口接收业务关联、接收人、事件键、模板、有效截止时间及业务版本。建议增加受服务身份保护的 M1 通知有效性查询，供 D 在实际投递前检查。

投递前检查与外部渠道接受之间仍存在不可消除的短暂竞态，不能承诺撤回已发送消息。

### 5.6 前端流程

建议页面：

- 座位搜索与预约确认；
- 我的预约、详情及签到；
- 历史与违约记录；
- 管理员预约和使用统计；
- 参数设置；
- D 空间、座位及开放规则管理；
- 受控签到编码展示。

实现要求：

- 共用统一登录、布局和请求客户端。
- `allowed_actions` 控制展示，服务端始终复核。
- 预约冲突时保留筛选条件并重新加载，不显示成功。
- 超时重试保留创建幂等键。
- 明确区分本人取消、未签到违约、系统维修取消和使用中断。
- 历史复用只预填座位，必须重新选择日期时间。
- 展示加载、空数据、失效会话、依赖错误和重复提交状态。
- 学生页面不得加载管理员签到编码接口。
- 不在页面、日志或前端常量中硬编码用户、院系或业务资源。

## 6. 详细开发任务清单

以下文件均按“现有需修改”或“建议新增”标明。每个任务的完成条件均包含对应行为验证及人工检查；不默认授权 Coding Agent 自动提交。

### M1-T01：建立一致的需求与决策基线

- **目标/需求**：固定本计划全部需求、边界和假设。
- **依赖**：无。

### M1-T02：建立最小工程、配置和测试入口

- **依赖**：T01。

- **验收**：应用可启动；健康检查及数据库 readiness 区分；前端可构建；真实数据库连接测试有效；启动所需变量有脱敏示例。
- **风险**：readiness 不等于业务验收；示例不包含可用凭据。

### M1-T03：接入 D 身份、会话和统一授权

- **验收**：未认证、无权限、跨院系、越界管理员、伪造身份、角色撤销均被拒绝；不同角色的动作与范围不能错误拼接。
- **风险**：这是外部协作任务，不能由 M1 私建替代认证；缺失时阻断真实受保护链路。

## 7. 分阶段执行 Roadmap

| 阶段 | 目标与顺序 | 前置条件 | 交付物和进入下一阶段的门槛 |
|---|---|---|---|
| Phase 0：规则收敛 | T01 | 原规划；本轮已获用户授权先实施提案 | 需求、技术和资源契约经评审；责任落实到人；缺失任务书明确记录 |
| Phase 1：真实基础链路 | T02 → T03/T04；同步启动 T06 公共契约 | 技术基线确定 | 登录后读取数据库真实教室；权限拒绝有效；基础 CI 可运行 |
| Phase 2：预约闭环 | T05/T06 → T07 → T08 → T09；T14 搜索预约部分跟进 | 身份、主数据、公共任务接口可用 | 浏览器搜索、预约、取消、历史可用；并发和隔离通过 |
| Phase 3：签到与自动处理 | T10 → T11；T14 完成 | 预约闭环通过 | 编码签到、三个时点、违约、正常结束和重启恢复通过 |
| Phase 4：跨模块与管理 | T12、T13 → T15；T14 收尾 | 公共通知和审计真实实现可用 | M2/M3 契约、维修免责处理、资源管理及统计可用；来源隔离通过 |
| Phase 5：联合验收与发布准备 | T16 → T17 最终门禁 | 实际 M2/M3 服务部署 | 真实网络链路、故障恢复、迁移、E2E及部署证据齐全，人工验收 |

可并行的工作：

- T01 完成后，D 身份、通知、审计提供方与 M1 工程建设可以按契约分别推进。
- 前端在 API 契约固定后开发页面和组件；业务完成仍须真实联调。
- M2/M3 可以在资源契约确定后开发调用方，不必等待 M1 管理页面完成。
- 同一迁移历史及同一资源内核的修改由指定维护者协调，避免并行产生冲突。

保持阶段可运行：

- 新增未完成页面不进入正式导航。
- 未完成业务入口不返回伪造成功。
- 每个阶段合入前保持构建及已有行为测试通过。
- 公共契约变更先更新调用方和兼容测试，再发布。
- 全组环境不得由 M1 单独重置数据库或覆盖部署。

不承诺未经成员容量核实的日历工期。实施 Issue 可以在上述依赖基础上补充负责人、估算和日期。

## 8. 测试与验收计划

### 8.1 分层验证

| 层次 | 核心验证 |
|---|---|
| 单元测试 | 区间重叠、开放区间覆盖、状态转换、编码日期、统计裁剪及通知有效期 |
| MySQL 集成测试 | 约束、事务回滚、真实并发、幂等、墓碑、租约及迁移 |
| API 测试 | 认证、授权、字段校验、所有权、错误响应、信息最小化 |
| 前端组件测试 | 表单校验、重复提交、错误展示、动作可见性及复用预填 |
| E2E | 登录到预约、取消、签到、历史及管理闭环 |
| 模块集成 | 实际 M2/M3 发起 HTTP 调用，核对资源和业务结果 |

不使用 SQLite 替代关键 MySQL 事务和约束测试。

### 8.2 必须执行的场景矩阵

| 类别 | 必测场景与期望 |
|---|---|
| 身份 | 未登录、停用账号、失效身份、伪造他人身份均拒绝 |
| 权限 | 猜测他人预约 ID、跨院系搜索/提交、跨范围管理、权限撤销、不同授权错误拼接均拒绝 |
| 开放规则 | 起点开放但终点关闭、区间中途闭馆、特殊关闭、跨午夜、午夜终点 |
| 时间参数 | 非整点、零/负时长、超过最大时长、过去时段、提前窗口边界 |
| 并发预约 | 至少 20 个独立请求竞争同座位同区间，最终恰好一个预约及一份有效占用 |
| 时间重叠 | 包含、被包含、部分交集冲突；首尾相邻不冲突；M2 非整点交集正确 |
| 幂等 | 相同请求重试不重复；同键异载荷拒绝；响应丢失后能返回原结果 |
| 取消 | 非本人、开始时刻、已签到拒绝；重复取消不重复释放 |
| 签到 | 错码、错教室、旧日期、轮换失效、失败限频、窗口两端及重复签到 |
| 定时 | 三个时点前后、Worker 重启、重复领取、租约到期和长延迟补处理 |
| 竞态 | 签到/超时、取消/超时、维修/签到、维修/预约、维修/未签到处理 |
| 维修免责 | 未签到取消、已签到中断、实际时长保留、无违约、未来预约影响和通知 |
| 多来源 | 双维修工单只解除一张仍下架；维修解除后管理员封闭或 M2 占用仍有效 |
| 乱序 | 先释放后旧添加、相同 revision 异载荷、高 revision 跳号、来源终止后重用 |
| M2 | 最终占用前重检；冲突失败不写部分明细；释放不影响其他来源 |
| 主数据 | 座位新增不绕过整室限制；注销保留历史；规则变更引发正确免责处理 |
| 通知 | 三个时点、事件去重、失败重试、签到/取消后失效、过期不补发旧提醒 |
| 审计 | 成功、失败及拒绝的必要关联可查；普通主体无法改写；敏感字段不入日志 |
| 统计 | 管理范围先过滤；取消、违约、中断分别计数；实际时长裁剪正确 |
| 投影 | 汇总缺失、旧版本、乱序计算不能产生错误可预约结果 |
| 迁移 | 空库、前版、有数据升级、重复种子、失败恢复及历史关联 |
| 网络集成 | 至少完整演示 M3 开始维修→M1 下架→验收一张仍受限→全部解除后再判断可用 |

### 8.3 关键规则破坏性验证

在隔离测试环境临时进行以下变更，并确认指定测试失败：

1. 去掉教室互斥或冲突检查，双成功测试失败。
2. 将释放改成“整室全部可用”，多工单及叠加来源测试失败。
3. 去掉所有权过滤，越权详情测试失败。
4. 去掉 revision 检查，旧添加复活测试失败。
5. 去掉违约唯一保护或条件更新，重复超时测试失败。
6. 去掉投递前有效性判断，签到后旧提醒测试失败。

每次恢复实现后重新验证；不提交破坏版本。保存真实命令、失败和恢复结果。

## 9. 风险、待确认事项与设计取舍

### 9.1 已确定的规划方向

| 事项 | 本次结论 |
|---|---|
| 前端和数据库 | TypeScript + MySQL 8.4 |
| 资源维护责任 | M1 组承担 D 空间资源子域 |
| 个人预约与资源协调 | 同服务公开接口、同数据库事务 |
| 维修影响个人预约 | 未签到免责取消，已签到免责中断 |
| M2/M3 集成方式 | 真实 HTTP，独立来源和操作标识 |

### 9.2 开发或发布门禁

| 事项 | 门禁与处理 |
|---|---|
| 技术、公共 schema、来源接口共同评审 | 用户已授权本轮任务分支实作提案；共同评审在合并前完成，不把用户授权写作全组批准 |
| D 到人责任、接口维护和故障责任 | 本轮登记为待定（用户已明确授权先实作）；到人资料由人工在合并前补齐 |
| D 身份实现与服务身份 | T03 的真实链路门禁；不以硬编码主体替代 |
| 任务书原件 | 不阻断基础实现，但在宣称课程需求完整符合前必须核验 |
| 通知渠道 | 首版建议实现真实站内通知，D 负责人确认课程是否另需邮件/微信；最终提醒验收不能只看日志 |
| 数据保留和清理 | 首版不自动物理删除历史；测试使用虚构数据。真实个人数据上线前确定访问、期限、归档和清理政策 |
| M2 既有活动遇维修 | 由 M2/M3 共同确认处理方式；M1 不擅自撤销 M2 申请 |
| 实际 M2/M3 可用性 | 最终 INT 验收门禁；缺失时明确报告未完成 |

### 9.3 主要技术与伦理风险

- **公共依赖需要共同维护**：已有 D 实现并不代表全部业务契约已验收，M1 后续交付仍须包含集成工作量。
- **MySQL 适配影响全组**：必须统一 ID、时间、JSON 和迁移，不保留两套数据库口径。
- **教室锁吞吐量有限**：先测量，未出现证据前不引入 Redis 或拆分锁粒度。
- **维修结束未知**：可能取消多天未来预约，这是保守安全策略；须在产品提示和团队评审中明确。
- **每日编码可转发**：提供限频、轮换和审计，但不宣称绝对防代签。
- **通知无法绝对撤回**：投递前核验失效，保留渠道接受时间和结果。
- **系统故障造成违约争议**：保留原因和可追溯证据；首版不增加自动封禁或经济处罚。
- **公平性规则尚未成熟**：每人额度、重复占座、累计违约处置保留后续评审，不让 Coding Agent自行加入处罚。
- **汇总数据陈旧**：只影响查询效率，不能改变提交裁决。
- **历史与隐私冲突**：保留追溯所需关联，通过 D 权限和后续归档政策控制访问，不复制学生个人信息。
- **团队工作区变化**：实施前重核状态；遇代码冲突交由人工，不自动解决。
