# 第一次功能迭代：M3 报修工单表设计

> **版本：第一次功能迭代（Iteration 1）**  
> 日期：2026-10-21。数据库统一为 **MySQL 8.4 + InnoDB + utf8mb4**。  
> 本文件是待团队确认的最小实现设计，不是最终需求完成声明；仅提供设计，不执行建表。

## 1. 本轮目标

上报 → 管理员派单 → 指定维修人员开始 → 提交完工 → 管理员验收；维修影响整室新预约。

| 本轮实现 | 后续必须补齐 |
|---|---|
| 文字上报、查询、派单、维修、完工、验收 | 超时升级、评价、通知 |
| 维修限制添加/释放、多工单叠加 | 附件、细粒度管理范围 |
| 最小操作历史、权限检查 | 独立事件表、网络调用与可靠补偿 |

只建 **1 张业务主表**，不额外建立评价、升级、附件、Outbox 表。

## 2. 字段设计

### `m3_work_orders`：报修工单

| 字段 | MySQL 类型 | 可空 | 说明／约束 |
|---|---|---|---|
| `id` | BIGINT UNSIGNED | 否 | 自增主键 |
| `created_at` | DATETIME(3) | 否 | 创建时间，UTC |
| `reporter_id` | BIGINT UNSIGNED | 否 | FK → d_users.id，从登录身份获取 |
| `room_id` | BIGINT UNSIGNED | 否 | FK → d_rooms.id |
| `title` | VARCHAR(100) | 否 | 故障标题 |
| `description` | TEXT | 否 | 故障描述，服务端限制 2000 字 |
| `category` | VARCHAR(24) | 否 | AIR_CONDITIONING / LIGHTING / POWER_SOCKET / FURNITURE / OTHER |
| `status` | VARCHAR(24) | 否 | REPORTED / ASSIGNED / REPAIRING / WAIT_ACCEPTANCE / COMPLETED |
| `assignee_id` | BIGINT UNSIGNED | 是 | FK → d_users.id，须为有效维修人员 |
| `assigned_by` | BIGINT UNSIGNED | 是 | FK → d_users.id |
| `assigned_at` | DATETIME(3) | 是 | 派单时间 |
| `started_at` | DATETIME(3) | 是 | 开始维修时间 |
| `completion_note` | TEXT | 是 | 最近一次完工说明 |
| `submitted_at` | DATETIME(3) | 是 | 最近一次提交验收时间 |
| `completion_round` | INT UNSIGNED | 否 | 默认 0；每次提交完工递增，用于识别验收批次 |
| `accepted_by` | BIGINT UNSIGNED | 是 | FK → d_users.id，验收通过人 |
| `accepted_at` | DATETIME(3) | 是 | 验收通过时间 |
| `acceptance_comment` | VARCHAR(500) | 是 | 最近一次验收意见，驳回必填 |
| `request_key` | CHAR(36) | 否 | 创建请求 UUID |
| `updated_at` | DATETIME(3) | 否 | 更新时间，UTC |

- UNIQUE(reporter_id, request_key)。索引 (reporter_id, created_at)、(assignee_id, status)、(room_id, status)。
- REPAIRING/WAIT_ACCEPTANCE 均应有 ACTIVE 的 M3 教室来源，end_at 为空。
- 首次开始维修创建一个来源；验收驳回继续使用原来源，不重复创建。
- COMPLETED 时该来源 RELEASED；其他有效来源仍然保留。
- 主表只保存最近说明，每次完工和验收意见同时追加到 d_operation_logs，防止覆盖历史。

## 3. 权限与流转

| 操作 | 允许角色/归属 | 状态变化 | 资源变化 |
|---|---|---|---|
| 上报 | USER；有效用户与身份 | 新建 REPORTED | 无 |
| 派单 | PROPERTY_ADMIN | REPORTED → ASSIGNED | 无 |
| 开始维修 | 被分配的 REPAIRER | ASSIGNED → REPAIRING | 添加本工单整室限制 |
| 提交完工 | 被分配的 REPAIRER | REPAIRING → WAIT_ACCEPTANCE | 保留限制 |
| 验收通过 | PROPERTY_ADMIN | WAIT_ACCEPTANCE → COMPLETED | 只撤销本工单限制 |
| 验收驳回 | PROPERTY_ADMIN | WAIT_ACCEPTANCE → REPAIRING | 保留限制，原因必填 |

- PROPERTY_ADMIN 本轮管理本组全部测试教室；避免维修人员本人兼任本单验收人，服务端拒绝自验收。
- 上报人看自己的工单；维修人员看分配给自己的；物业管理员看全部测试工单。
- 允许多个工单作用同一教室，不能把“工单已完成”直接等同于“教室可预约”。
- 本轮不自动取消已有 M1/M2 使用记录，新增维修限制只阻止新预约/新批准；详情和汇报明确说明这一待完善策略。
- 不实现撤销、转派和完成后重开。重复请求不得让已完成工单重新激活。

## 4. 接口与页面

| 方法 | 路径 | 功能 |
|---|---|---|
| POST | /api/v1/m3/work-orders | 创建 |
| GET | /api/v1/m3/work-orders | 按身份过滤列表 |
| GET | /api/v1/m3/work-orders/{id} | 详情及有权查看的操作历史 |
| POST | /api/v1/m3/work-orders/{id}/assign | 派单，body 含 assignee_id |
| POST | /api/v1/m3/work-orders/{id}/start | 开始维修 |
| POST | /api/v1/m3/work-orders/{id}/submit-completion | 提交 completion_note |
| POST | /api/v1/m3/work-orders/{id}/acceptance | passed、comment、expected_completion_round |

前端只做“工单列表＋详情”两类页面，列表按角色切换；上报、派单、完工、验收用弹窗。

## 5. 事务与幂等

所有写操作统一房间锁 → 工单锁 → 校验当前状态/操作人。

- 开始：同事务更新 REPAIRING、写 M3 来源、日志和资源版本，不需要准备维修异步状态。
- 验收通过：同事务更新 COMPLETED、释放本工单来源、日志和资源版本。
- 完工/驳回：写状态和日志，继续保留原限制。
- 重复开始在已经 REPAIRING 时返回当前结果，不新增来源；重复通过在已 COMPLETED 时返回当前结果。
- 与当前状态矛盾的旧请求返回 409。每次提交完工递增 completion_round；验收接口提交 expected_completion_round，后端与当前轮次比较，必须匹配，避免旧验收请求误处理新一轮完工。

第一轮同进程、同数据库事务保证一致性；网络化后必须另行设计同步确认和失败恢复，不能照搬本轮事务范围。

## 6. 验收

- 完整跑通一张工单；非法角色及错误状态操作被拒绝。
- 开始维修后 M1 新预约和 M2 冲突审批被拒绝。
- 完工待验收期间仍不可新预约。
- 两张维修工单只验收一张，仍不可新预约；全部关闭且无其他限制后恢复。
- 重复开始/通过不产生重复来源或误释放。
- 旧验收请求不能处理后续重新提交的完工批次。
- 不在首次汇报中声称超时升级、评价和通知已完成。
