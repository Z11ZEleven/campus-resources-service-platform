# 第一次功能迭代：M2 教室申请审批表设计

> **版本：第一次功能迭代（Iteration 1）**  
> 日期：2026-10-21。数据库统一为 **MySQL 8.4 + InnoDB + utf8mb4**。  
> 本文件是待团队确认的最小实现设计，不是最终需求完成声明；仅提供设计，不执行建表。

## 1. 本轮目标

教师提交整室申请 → 教室管理员单级通过/驳回 → 通过后同室时段不能个人预约。

| 本轮实现 | 后续必须补齐 |
|---|---|
| 提交、本人查询、管理员单级审批、待审撤销 | 多级审批与审批流程版本 |
| 校验容量、资格与真实资源冲突 | 超时自动撤销、通知与细粒度审批范围 |
| 通过后写入公共整室来源 | 已通过申请的撤销规则与网络集成 |

只建 **1 张业务主表**。本轮单级审批不是最终任务书中的多级审批完成版。

## 2. 字段设计

### `m2_applications`：整教室申请单

| 字段 | MySQL 类型 | 可空 | 说明／约束 |
|---|---|---|---|
| `id` | BIGINT UNSIGNED | 否 | 自增主键 |
| `created_at` | DATETIME(3) | 否 | 创建时间，UTC |
| `applicant_id` | BIGINT UNSIGNED | 否 | FK → d_users.id，从登录身份获取 |
| `room_id` | BIGINT UNSIGNED | 否 | FK → d_rooms.id |
| `title` | VARCHAR(100) | 否 | 活动/申请名称 |
| `purpose` | TEXT | 否 | 用途说明 |
| `participant_count` | INT UNSIGNED | 否 | 人数，大于 0，不能超过教室容量 |
| `start_at` | DATETIME(3) | 否 | 使用开始，UTC |
| `end_at` | DATETIME(3) | 否 | 使用结束，UTC |
| `status` | VARCHAR(16) | 否 | PENDING / APPROVED / REJECTED / CANCELLED |
| `reviewer_id` | BIGINT UNSIGNED | 是 | FK → d_users.id，审批人 |
| `reviewed_at` | DATETIME(3) | 是 | 审批时间 |
| `review_comment` | VARCHAR(500) | 是 | 审批意见，驳回必填 |
| `cancelled_at` | DATETIME(3) | 是 | 待审撤销时间 |
| `request_key` | CHAR(36) | 否 | 创建请求 UUID |
| `updated_at` | DATETIME(3) | 否 | 更新时间，UTC |

- UNIQUE(applicant_id, request_key)，索引 (applicant_id, created_at)、(status, created_at)、(room_id, start_at)。
- PENDING 不预占；APPROVED 才有 source_module = M2 的有效资源来源，seat_id 为空。
- 已通过但使用时间已结束时，响应中计算 display_status = ENDED，不依赖定时任务变更主状态。
- 审批结果保存在主表；提交、审批、撤销轨迹写 d_operation_logs。

## 3. 权限与规则

- 具有 USER 角色的有效 TEACHER 身份可以申请；其他身份本轮不开放申请资格，后续按团队决定配置。
- ROOM_ADMIN 可审批本组测试教室，但不能审批本人申请；种子数据准备不同账号。
- 起止均为北京时间整点、同一天且未来，位于开放时间内；M2 不沿用 M1 的 4 小时上限，只要求同日开放时段内。
- 所有使用方都遵守教室院系限制；确需跨院系借用另行评审。
- 申请提交时可初步提示冲突，最终通过时必须锁房间后重新检查。
- 已有 M1/M2/M3 冲突：返回 409，申请仍为 PENDING，管理员可明确驳回；不自动取消已有预约。
- 本轮仅 PENDING 可由申请人撤销；APPROVED 不提供撤销入口，时间到后自然不再限制后续时段。

## 4. 状态流转

| 当前状态 | 操作 | 结果 |
|---|---|---|
| PENDING | 通过且资源无冲突 | APPROVED，并创建整室来源 |
| PENDING | 驳回 | REJECTED，记录意见 |
| PENDING | 本人撤销 | CANCELLED |
| APPROVED/REJECTED/CANCELLED | 再次审批 | 同决定可幂等返回；相反决定返回 409，不重开 |

## 5. 接口与页面

| 方法 | 路径 | 行为 |
|---|---|---|
| POST | /api/v1/m2/applications | 提交申请 |
| GET | /api/v1/m2/applications | 本人列表；ROOM_ADMIN 可查全部测试申请 |
| GET | /api/v1/m2/applications/{id} | 权限过滤详情 |
| POST | /api/v1/m2/applications/{id}/review | body 含 passed、comment |
| POST | /api/v1/m2/applications/{id}/cancel | 本人撤销待审申请 |

前端：我的申请/新建弹窗、管理员待审批列表/审批弹窗。

## 6. 审批事务

开启事务 → 锁 d_rooms 行 → 锁申请并复查 PENDING → 校验审批人、开放时段、院系、容量及未来时间 → 检查同室重叠来源 → 更新 APPROVED → 创建 M2 整室来源 → 写日志与资源版本 → 一起提交。

驳回和撤销同样按房间再业务单的顺序加锁，防止与审批发生竞态。

## 7. 验收

- 不同账号完成一次申请与通过，再验证同室 M1 被阻止。
- 已有 M1 占用时不能批准冲突 M2；相邻时段允许。
- 驳回/待审撤销不产生资源占用。
- 重复通过不重复创建来源；未授权和自审操作被拒绝。
- 明确多级审批、超时撤销尚待后续实现。
